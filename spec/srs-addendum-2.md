## 1. Призначення та підстава для створення Addendum #2

Після досягнення повного базового функціоналу REST API v1 (`GATE-04`, вимоги `REQ-F-001` – `REQ-F-021`) виникла потреба надати користувачеві можливість прибирати застарілі або непотрібні вправи з активного довідника каталогу без порушення історичної цілісності тренувань.

Фізичне видалення (`HARD DELETE`) запису з таблиці `exercises` призводить до ризику **`RSK-10`**: каскадного знищення або пошкодження зовнішніх ключів (`foreign keys`) у раніше збережених блоках тренувальних сесій та неможливості побудови історичних графіків аналітики.

Відповідно до методології **Specification-Driven Development (SDD)**, зміна вноситься керовано — через формалізацію нової вимоги **`REQ-F-022`**, критерію прийняття **`AC13`**, поведінкового сценарію **`BDD-008`** та ризику **`RSK-10`** із патерном **Soft Delete** перед оновленням кодової бази.

## 2. Формалізована додаткова функціональна вимога (`REQ-F-022`)

* **ID Вимоги:** `REQ-F-022`
* **Назва:** М'яке видалення (архівація) вправи з каталогу зі збереженням історичної цілісності.
* **Специфікація поведінки:**
  1. Система повинна надавати можливість видалення (архівації) вправи з каталогу за її ідентифікатором (`DELETE /api/v1/exercises/{exerciseId}`).
  2. Операція виконується за патерном **Soft Delete**: вправа позначається як архівована (`is_archived = true`, фіксується мітка часу `archived_at`), але фізично залишається в базі даних для збереження посилальної цілісності (`foreign keys`) усіх раніше створених блоків та історичних графіків аналітики.
  3. Архівовані вправи автоматично виключаються зі списку активного каталогу (`GET /api/v1/exercises`), щоб не засмічувати вибір під час тренування.
  4. Система забороняє додавати архівовану вправу до нових тренувальних сесій (`POST /api/v1/sessions/{sessionId}/blocks`) із поверненням доменної помилки `422 Unprocessable Entity` (`ERR_EXERCISE_ARCHIVED`).
  5. Історичні сесії (`GET /api/v1/sessions/{sessionId}`) та аналітичний дашборд (`GET /api/v1/exercises/{exerciseId}/analytics`) продовжують коректно повертати дані для архівованої вправи без втрати історії.
  6. Повторний виклик `DELETE /api/v1/exercises/{exerciseId}` для вже архівованої або неіснуючої вправи повертає `404 Not Found` (`ERR_RESOURCE_NOT_FOUND`).

## 3. Критерій прийняття (`AC13`) та BDD-сценарій (`BDD-008`)

| ID Критерію | Пов'язана вимога | Умова прийняття (Observable Condition) |
| :--- | :--- | :--- |
| **AC13** | `REQ-F-022` | `DELETE /api/v1/exercises/{exerciseId}` архівує вправу (`200 OK`), приховує її з `GET /api/v1/exercises`, блокує додавання в нові сесії (`422 ERR_EXERCISE_ARCHIVED`), але повністю зберігає її дані в існуючих сесіях та аналітиці. Повторний виклик `DELETE` повертає `404 ERR_RESOURCE_NOT_FOUND`. |

### Поведінковий сценарій `BDD-008`

```text
Сценарій: Архівування вправи приховує її з каталогу, але зберігає історію тренувань
Дано вправу 'Присідання зі штангою', яка вже використовувалася в минулій тренувальній сесії
Коли користувач видаляє (архівує) цю вправу з каталогу через DELETE /api/v1/exercises/{exerciseId}
Тоді система повертає статус 200 OK із позначкою архівації
І вправа більше не відображається у списку активних вправ GET /api/v1/exercises
І спроба додати цю вправу в нову сесію відхиляється з кодом 422 (ERR_EXERCISE_ARCHIVED)
Але історична сесія та аналітика цієї вправи залишаються повністю доступними
```

## 4. Пов'язані ризики та матриця простежуваності

* **Пов'язаний ризик (`RSK-10`):** Порушення цілісності історичних сесій, зовнішніх ключів СКБД (`foreign keys`) та втрата графіків аналітики у разі фізичного видалення вправи з довідника.
  * **Мітигація:** Суворе застосування патерну Soft Delete (`is_archived = true`, `archived_at`) без фізичного видалення рядків з таблиці `exercises`, обов'язкова верифікація через сценарій `BDD-008`.
