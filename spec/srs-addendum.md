## 1. Призначення та підстава для створення Addendum

Під час проєктування контракту REST API (`docs/api-design.md`) було проведено перехресну верифікацію функціональних вимог (`REQ-F-001` – `REQ-F-018`) із сутностями **Глосарію предметної області** та кроками затверджених **BDD-сценаріїв** (`BDD-001` – `BDD-007`).

У результаті виявлено три змістовні прогалини, де операції та правила неявно використовуються у сценаріях перевірки, але не мали власних формалізованих ідентифікаторів `REQ-F`:
1. Механізм перегляду й ручного оновлення поточної маси тіла в профілі користувача (необхідний для виконання передумов `REQ-F-002` та кроку `BDD-001`).
2. CRUD-операції над довідником (каталогом) вправ із фіксацією біомеханічного типу вправи (`STANDARD`, `BODYWEIGHT`, `ASSISTED`), на який спираються `REQ-F-008` – `REQ-F-013`.
3. Формалізація ефективної розрахункової ваги ($W_{eff}$) у формулах 1RM для вправ із власною вагою/компенсацією та правила визначення базового блоку при обчисленні Дельти.

Згідно з методологією **Specification-Driven Development (SDD)**, заборонено проєктувати контракти чи писати код для неформалізованої поведінки. Цей документ офіційно розширює специфікацію `spec/srs.tex` вимогами **`REQ-F-019`**, **`REQ-F-020`** та **`REQ-F-021`**.

## 2. Формалізовані додаткові функціональні вимоги

### 2.1. Управління профілем користувача (`REQ-F-019`)

* **ID Вимоги:** `REQ-F-019`
* **Назва:** Управління профілем користувача та поточною масою тіла.
* **Специфікація поведінки:**
  1. Система повинна надавати можливість отримання (`GET`) та оновлення (`PUT`) поточної маси тіла користувача (`current_body_weight`) у його глобальному профілі (`User Profile`).
  2. **Валідаційні межі:** Значення `current_body_weight` повинно лежати у допустимому фізичному діапазоні від **`30.0` до `300.0` кг** включно ($30.0 \le \text{current\_body\_weight} \le 300.0$). Спроба зберегти значення поза цими межами повинна відхилятися системою з кодом помилки доменної валідації (`422 Unprocessable Entity`, `ERR_INVALID_BODY_WEIGHT`).
  3. **Інваріант історичної незмінності (Immutability Invariant):** Оновлення поля `current_body_weight` у профілі користувача застосовується виключно для формування снапшотів у майбутніх тренувальних сесіях. Система суворо забороняє будь-яку мутацію або перерахунок збережених значень `body_weight_snapshot` у раніше створених сесіях (забезпечення виконання `REQ-F-002`, сценарію `BDD-001` та нейтралізація ризику `RSK-06`).

---

### 2.2. Управління каталогом вправ (`REQ-F-020`)

* **ID Вимоги:** `REQ-F-020`
* **Назва:** Реєстрація та перегляд вправ у довіднику (Exercise Catalog).
* **Специфікація поведінки:**
  1. Система повинна дозволяти створення нової вправи в каталозі із обов'язковим зазначенням унікальної назви (`name`) та її біомеханічного типу (`exercise_type`), який приймає одне з трьох значень:
     * `STANDARD` (Вільні ваги / Тренажери);
     * `BODYWEIGHT` (Власна вага з можливим додатковим обтяженням);
     * `ASSISTED` (Вправи з компенсацією ваги / противагою, зокрема у гравітроні).
  2. Система повинна надавати можливість отримання повного списку зареєстрованих вправ каталогу (з опціональною фільтрацією за `exercise_type`) та перегляду деталей і налаштувань окремої вправи за її ідентифікатором (`exercise_id`).
  3. **Правило дефолту моделі 1RM:** Відповідно до `REQ-F-013`, якщо під час створення вправи користувач явно не вказав математичну модель розрахунку 1RM (`rm_model`), система автоматично встановлює значення `"EPLEY"`.

---

### 2.3. Ефективне навантаження для 1RM та правила розрахунку Дельти (`REQ-F-021`)

* **ID Вимоги:** `REQ-F-021`
* **Назва:** Уточнення розрахункової бази 1RM для Bodyweight/Assisted вправ та хронологічної бази Дельти.
* **Специфікація поведінки:**
  1. **Уточнення до `REQ-F-011` (Ефективна вага у формулах 1RM):**
     Під час обчислення показника одноповторного максимуму (`1RM`) за формулами Epley та Brzycki як змінна ваги $W$ використовується **ефективне навантаження (`effective_weight`, $W_{eff}$)**:
     * Для вправ типу `STANDARD`:
       $$W_{eff} = W_{added} \quad (W_{added} > 0)$$
     * Для вправ типів `BODYWEIGHT` (`W_{added} \ge 0`) та `ASSISTED` ($W_{added} \le 0$):
       $$W_{eff} = \text{body\_weight\_snapshot} + W_{added} \quad (W_{eff} > 0)$$
     * Відповідно, розрахунок 1RM для робочих підходів (`is_warmup == false`) здійснюється за формулами:
       * **Epley:** $\text{1RM} = W_{eff} \times \left(1 + \frac{R}{30}\right)$
       * **Brzycki:** $\text{1RM} = W_{eff} \times \left(\frac{36}{37 - R}\right), \quad \text{де } 1 \le R \le 36$
  2. **Уточнення до `REQ-F-015` та `REQ-F-016` (Хронологічна база розрахунку Дельти):**
     Оскільки одиницею агрегації метрик згідно з `REQ-F-006` є ізольований блок вправи (`ExerciseBlock`), базою порівняння (Baseline) для обчислення `volume_load_delta` та `max_1rm_delta` поточного блоку є **останній попередній за часом створення блок цієї ж вправи (`exercise_id`)**, що містить щонайменше один робочий підхід. Хронологічний порядок визначається комбінацією часу початку сесії (`started_at`) та порядкового номера блоку всередині сесії (`order_index`).

## 3. Додаткові критерії прийняття (Acceptance Criteria)

| ID Критерію | Пов'язана вимога | Умова прийняття (Observable Condition) |
| :--- | :--- | :--- |
| **AC10** | `REQ-F-019` | `GET /api/v1/profile` повертає поточну вагу; `PUT /api/v1/profile` приймає значення у межах `[30.0, 300.0]` кг, повертає `422` поза межами та залишає незмінними `body_weight_snapshot` усіх раніше створених сесій. |
| **AC11** | `REQ-F-020` | `POST /api/v1/exercises` створює вправу з типом `STANDARD \| BODYWEIGHT \| ASSISTED` і дефолтною моделлю `EPLEY`; `GET /api/v1/exercises` та `GET /api/v1/exercises/{exerciseId}` повертають збережені вправи. |
| **AC12** | `REQ-F-021` | Для підходу в гравітроні (`body_weight_snapshot = 80`, `weight = -20`, `reps = 10`) ефективна вага становить `60.0` кг, а розрахунковий 1RM (Epley) становить $60 \times (1 + 10/30) = 80.0$ кг. Дельта блоку обчислюється відносно попереднього хронологічного блоку тієї ж вправи. |
